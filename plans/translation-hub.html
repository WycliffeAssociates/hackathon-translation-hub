Proposal · Translation Hub · combined draft

One language, 346 catalog entries. Which one is the Bible?

A web application on top of WACS that gives every Bible version a home: one official repo per version, a clear view of every draft that could feed it, and a live connection to the gateway sources it was translated from.

In the official repo Only in a draft repo In two or more draft repos Not started

Every square is one chapter. This is the picture a translation lead should be able to see for their version in a single glance — today it has to be assembled by hand.

The problem

WACS holds the work, but not the relationships between pieces of work. A translation team's Bible is spread across single-book BTT-Writer repos, consolidated repos, staging copies and personal mirrors, and nothing in the system says which of them is the version people should read, print or build on.

A quick look at the public catalog API for one gateway language, Khmer, shows the shape of it:

346catalog entries for Khmer
2owners each holding a repo named km_ulb
2×Isaiah and Haggai, each in Staging and in a personal mirror
18heart languages that depend on Khmer as a gateway

The "primary" flag in our internal tracker tries to paper over this, but because single-book Writer repos need to be primary too, and nothing prevents two consolidated repos from both being flagged, it can't give a single answer. Consolidation is a manual staff task, which makes it a bottleneck at exactly the point where we want work to flow in from many places.

Meanwhile the gateway-language strategy creates a dependency graph — English alone is a gateway for 1,774 languages in the catalog, French for 1,103 — but when a gateway text changes, there's no channel to tell the teams downstream what changed or why it matters.

Vocabulary

"Translation" means both a process and a product, which makes conversations slippery. The public already has a word for the product: the V in NIV, ESV and KJV stands for Version. The proposal uses these terms:

Version
A distinct, named translation of Scripture in one language with its own methodology and team — what this document has been calling a "translation effort." A language can have several, and each is keyed by its resource type, such as reg or ulb.
Track
One modality of a version: text or audio. Oral-only languages have only an audio track.
Official repo
The single repo the hub treats as the version's canonical content for a track, kept in a hub-managed Forgejo organization. Exactly one per track.
Draft source
Any repo that can contribute chapters to the official repo: BTT-Writer projects, other translators' repos, Orature projects, AI drafts.
Gateway source
A gateway-language text the version is translated from, pinned to a specific commit. One of them is the structural source that fixes versification.
Reference text
An extra text a person adds for their own reading, based on the languages on their profile. Personal, not part of the version.
Release
A published, numbered snapshot of a track, with rendered outputs.
Contribution request
A proposal to bring specific chapters from a draft source into the official repo, approved by the translation lead.
Bulletin
A note from a gateway-language team to every heart-language team that depends on them.

Who it's for

The primary user is the translation lead — often a pastor or church leader — who is responsible for a version but is not a software person. Every screen should make sense to them first. Translators are welcome and may work directly in the hub on a shared computer, but most will simply keep pushing from BTT-Writer, Sefer or Orature, and the hub picks up their work as draft sources.

Developers are not the primary users, but every screen is backed by the same public API, so other apps and agents get the same answers the lead sees.

Two consequences follow. First, "multiple primaries" becomes impossible by construction rather than by policy. Second, provenance makes "updates available" work the same way in both directions: a gateway source moved past its pinned commit, or a draft source has newer work on a chapter that was already brought in.

Core journeys

  1. Set up my languages. On first sign-in, a person picks the languages they speak, grouped by region, and marks which are gateway languages to them. The whole hub filters and suggests from this list.
  2. Find my version's home. The lead lands on the version homepage: coverage, gateway sources, new draft work, checks, releases, and buttons to open Sefer or Orature on the official repo.
  3. Bring in chapters. From the coverage map, the lead (or a translator) selects chapters from a draft source and sends a contribution request. Behind the scenes it's a branch and a Forgejo pull request; on screen it's a side-by-side read and an Approve button.
  4. Respond to a gateway change. A bulletin arrives from the gateway team with the affected chapters listed. The lead reviews the diff, marks it reviewed or flags chapters for revision, and the version's pin moves forward.
  5. Prepare a release. The lead proposes a release candidate. Checks run, the Scripture Accessibility team reviews outputs, and approval publishes it to the catalog.
  6. Request an AI draft. Once the New Testament is complete, staff or the lead request an Old Testament draft. It arrives as a new draft source and goes through the same review as human work.

Gateway to heart

Pinning each version's gateway sources to a commit turns the gateway strategy into something the hub can act on. When a gateway team publishes a release, the hub can compute which chapters changed, cross that with each heart-language version's coverage, and show every lead a short, specific list rather than a vague "the source was updated."

Bulletins add the human layer: the gateway team explains why something changed and what heart teams should think about. Over time this becomes a shared record of translation decisions that heart teams can learn from, and it gives gateway teams visibility into which dependent teams have reviewed their changes.

Publishing

A release moves through three states. Candidate: the lead tags the official repo and checks run. In review: the Scripture Accessibility team reviews rendered PDF and HTML outputs and formatting. Published: the tag is final, outputs are registered in the catalog, and the release becomes visible to the public and to the version's dependents if it is a gateway.

Release numbers belong to the version, not the repo, so "Western Cham Bible 1.0" means the same thing whether someone downloads the PDF, the audio, or the USFM.

What we build on

The hub is a separate web application, not a fork of Forgejo. It adds a small database of its own and leaves storage, accounts and history to the systems that already do them well. It never edits Forgejo's files directly: anything it writes goes through the Forgejo API, like any other client.

How it runs

Most technical choices can wait until the product is clear. These few shape everything else, so we want to settle them now.

Next to the files

The hub runs on the same server as Forgejo and reads the repos straight off disk, read-only. No git over the network, so looking across the whole catalog is cheap: indexing every repo takes well under a minute in early tests.

A soft poll, not webhooks

Every few minutes it asks Forgejo's database which repos changed. Webhooks in our ecosystem have been dropped when services restart or the network hiccups; a poll can't miss anything, and it's fast because everything is local.

Writes through the Forgejo API

Contribution requests, official-repo orgs and releases go through the API like any other client, so Forgejo stays the source of truth for content and permissions.

Rust API

The USFM parsing and linting Sefer already uses is written in Rust. The hub uses the same code instead of writing it again.

API first, with generated SDKs

The API publishes an OpenAPI spec, and we generate typed clients from it for TypeScript and Kotlin. Apps and agents stop needing to know how the WA catalog works or how to decide what counts as a source text.

SQLite

One database file next to the service, holding the Bible shape of every repo plus the hub's own records. We stay on SQLite until scale shows we can't. It can also be replicated into TypeScript clients.

Web front end

TypeScript, and not a single-page app. The framework is open.

// what a client sees instead of raw repo listings

Hackathon slice

A small, real piece of phase 1, built against about 1,500 real repos copied from the WACS dev server.

Goal: one version homepage, read-only, from real data

  • Index the repos next to the files: language, resource type, books and chapters present.
  • Group repos into versions by language and resource type.
  • Build the chapter coverage map for a version from what's on disk.
  • Serve it through the API, with an OpenAPI spec.
  • One page: the version homepage with the coverage map, its draft repos, and lint counts.

Out of the slice: sign-in, writes, bulletins and releases.

Open questions

Is chapter-level provenance redundant?

BTT-Writer already works in books, and Sefer already works on the whole repo. If the official repo is the one place chapters land, its git history (the commit, the pull request that merged it, and its author) may already record where each chapter came from.

Does provenance mean something beyond that? For example, Orature's chapter recordings, chapters pulled from many repos at once, or the person who did the work when that isn't the Forgejo user who pushed it?

  • How far do we aim the framing at the start: a home for versions, or the place most people use instead of the Forgejo web UI?
  • Which TypeScript framework for the front end, given that it isn't a single-page app? Solid 2 is a release candidate.
  • Who decides which repo becomes official for each version during migration, and what happens where two teams disagree?
  • Does a version always belong to one team, or can a lead hand it over? Who can create a new version in a language that already has one?
  • How should "Open in Sefer / Orature" work — a custom URL handler that opens the desktop app on the official repo, or a web build of Sefer?
  • When two drafts have the same chapter, is the lead's side-by-side comparison enough, or do we need verse-level picking from Sefer's merge code?
  • Should translators working on a shared computer each sign in, or can the lead record who did the work when bringing it in?
  • Do audio and text tracks of the same version share release numbers, or release independently?
  • What check results, if any, should block a release rather than just inform it?
  • Does any of the hub's own data belong in the catalog API too, so existing consumers can see it?
